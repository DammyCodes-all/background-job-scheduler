# Architecture: Background Job Scheduler

## System Overview

A background job scheduler that accepts jobs via REST API, orders them by priority and time, distributes them to a single in-process worker, and provides visibility into execution state via SSE and a dead-letter queue. Three components run inside the same Node.js process: the **API layer** (NestJS controllers and services), the **Scheduler** (a priority heap feeder that polls the database and keeps an in-memory min-heap populated), and the **Worker** (a recursive setTimeout loop that pops from the heap, claims the job via a pessimistic write lock, executes the handler, and handles success or failure). On startup, the scheduler and worker both begin running immediately. No external job queue, no Redis, no separate worker processes.

```
Client ──POST/GET──▶ API ──▶ PostgreSQL
                                ▲
                     Scheduler ──┘
                        │
                     [Min-Heap]
                        │
                     Worker ──▶ PostgreSQL
                        │
                     HandlersRegistry
```

A client creates a job via the API. The scheduler polls every 500ms for pending jobs whose `scheduledAt` is in the past and pushes them into the min-heap. The worker pops the highest-priority entry every 1s, claims it with `UPDATE ... WHERE status = pending` (the pessimistic lock), checks dependencies, runs the registered handler, and commits the result.

## Database Schema

### `jobs` table

The single source of truth. Every job lives here across all states: pending, processing, completed, failed, cancelled, or dead-letter. There are no separate queues, no retry topics, no DLQ table.

| Column | Type | Why |
|---|---|---|
| `id` | `uuid PK` | Generated by Postgres. UUIDs prevent sequential ID guessing and make cross-instance merging safe if the system ever splits. |
| `type` | `varchar` | The job kind: `send_email`, `generate_report`, etc. Maps 1:1 to a registered handler in `HandlersRegistry`. |
| `payload` | `jsonb nullable` | Arbitrary data the handler needs. JSONB lets us query into it if needed and avoids a separate `job_data` table. |
| `priority` | `int default 1` | Lower number = higher priority. 1 beats 2 beats 3. The heap sorts by this first. No upper bound enforced; starvation prevention can push this down to 1 (the floor). |
| `status` | `enum(pending,processing,completed,failed,cancelled)` | Drives the optimistic/pessimistic locking in the worker and filters in the scheduler query. Indexed together with `scheduledAt` and `priority` via a partial index that only covers `pending` rows. The scheduler never queries non-pending rows. |
| `retryCount` | `int default 0` | Incremented on each failure. Compared against `maxRetries` to decide whether to retry or DLQ. |
| `maxRetries` | `int default 3` | Per-job configurability. Some jobs are idempotent and can tolerate more retries; others should fail fast. |
| `scheduledAt` | `timestamptz default now()` | The scheduler only picks up jobs where `scheduledAt <= now()`. Retries work by setting this to `now + delay`. No separate retry mechanism needed. |
| `interval` | `varchar nullable` | `every_1_minute`, `hourly`, `daily`, etc. Null means one-shot. Non-null means a new job row is created on completion. |
| `dependencyIds` | `uuid[] default []` | Array of job IDs that must be `completed` before this job runs. Enforced at execution time: if deps are not met, the job is re-queued with a 10s delay. Cycle-checked at creation via DFS. |
| `errorMessage` | `text nullable` | Set on failure. Visible in the DLQ view so engineers can investigate without grepping logs. |
| `inDlq` | `boolean default false` | The dead-letter flag. No separate DLQ table. Set to `true` when `retryCount >= maxRetries`. |
| `createdAt` | `timestamptz` | Inserted by Postgres default. Used as the third-level heap sort key: among equal-priority, equal-scheduledAt jobs, the oldest wins. |
| `lastPriorityBoostedAt` | `timestamptz nullable` | Guards the starvation prevention sweep. A job is not boosted again if it was boosted within the last 30s. |
| `startedAt` | `timestamptz nullable` | Set when the worker claims the job. Useful for detecting stuck jobs (processing for too long with no heartbeat). |
| `completedAt` | `timestamptz nullable` | Set on successful completion. Metrics, dashboard, audit. |

**Partial index**: `IDX_JOBS_PENDING` on `(status, scheduledAt, priority) WHERE status = 'pending'`. The scheduler's feed query uses exactly these three columns in its WHERE and ORDER BY clauses. Without the partial filter, the index would be bloated with millions of completed/failed rows that the scheduler never reads.

### `job_logs` table

An append-only audit trail. Every state transition writes a row: created, processing, completed, failed, retry_scheduled, dependency_not_met, dlq_alert_triggered.

| Column | Type | Why |
|---|---|---|
| `id` | `uuid PK` | Standard primary key. |
| `jobId` | `uuid FK → jobs(id) ON DELETE CASCADE` | Cascading delete means removing a job cleans up its logs automatically. No dangling rows. |
| `event` | `varchar` | The event type: `processing`, `completed`, `retry_scheduled`, etc. Frontend uses this to color-code the timeline. |
| `message` | `text nullable` | Human-readable detail. Error messages, delay amounts, retry counts. |
| `createdAt` | `timestamptz` | When the transition happened. Auto-set by Postgres default. |

## Heap Implementation

### Why a min-heap instead of `ORDER BY priority, scheduledAt, createdAt LIMIT 1`?

A DB ORDER BY with LIMIT is an O(n log n) sort on every poll. With 10k pending jobs and a 500ms feed interval, that is a full table sort 120 times per minute. A heap is O(log n) insert and O(log n) pop. The DB query only runs to initially populate the heap (full scan on startup) and to refresh it (incremental query for jobs that are past their scheduledAt since the last poll). After that, all ordering happens in memory.

The tradeoff: the heap is not authoritative. It is a performance cache. The DB is always the source of truth. On restart, the heap is rebuilt from the DB.

### Three-level ordering

The comparison function sorts by:

1. **Priority** (lower first). High-priority jobs always come out first.
2. **scheduledAt** (earlier first). Among equal-priority jobs, the one that has been waiting longest wins. This is the starvation backstop: even a low-priority job eventually has the earliest scheduledAt.
3. **createdAt** (earlier first). Tiebreaker. Among equal-priority, equal-scheduledAt jobs, the oldest creation wins. FIFO within a slot.

### Push: bubble up

A `HeapEntry` (id, priority, scheduledAt, createdAt) is appended to the end of the heap array, then bubbles up: compare with parent, swap if the new entry has higher priority (lower number) or equal priority but earlier scheduledAt. Continues until the parent is higher-priority or the root is reached. O(log n).

### Pop: sift down

The root (highest-priority entry) is removed. The last element in the array is moved to the root, then sifts down: compare with children, swap with the higher-priority child, repeat until the node is in the correct position. The popped `HeapEntry` is then used to fetch the full `Job` from the database. O(log n).

### The `inHeap` set

A `Set<string>` of job IDs that are currently in the heap. Before pushing a job, the scheduler checks this set to avoid duplicates. The heap itself cannot efficiently answer "is this job already present?" That would be an O(n) scan. The `inHeap` set makes it O(1).

On `popNextJob()`, the ID is removed from the set. On `markRemovedFromHeap()` (used when a job is cancelled externally), the ID is removed from the set but the heap entry itself stays. Removing from the middle of a heap requires an O(n) rebuild or O(log n) mark-and-lazy-cleanup. The stale entry gets popped naturally on the next `popNextJob()`. When the worker tries to claim it, the pessimistic lock UPDATE finds the status is no longer `pending` and returns `affected = 0`. The worker silently skips it and moves on to the next entry.

## Scheduling Algorithm Comparison

### Heap (current implementation)

- Correct priority ordering across all dimensions
- O(log n) insert, O(log n) pop, O(1) peek
- In-memory, rebuilt from DB on restart
- No ordering guarantee within equal-priority slots beyond the tiebreaker (createdAt)

### Timing Wheel

- O(1) insert: append to a circular slot, no comparisons
- O(1) pop: advance a cursor, drain the current slot
- No ordering guarantee within a slot. Jobs in the same slot are FIFO at best, but their relative priority is lost.
- Best for high-throughput uniform scheduling where all jobs have similar priority
- Memory proportional to the number of slots multiplied by slot capacity

### Benchmark

Benchmark script is at `scripts/benchmark.ts`. Numbers to be added after timing wheel implementation.

### Which one in production?

Heap when priority ordering matters, which is most of the time for a job scheduler. If you need the highest-priority job out of 50k pending jobs, the heap always gives you the right one. The timing wheel shines in throughput-bound systems where all jobs have equal or near-equal priority (e.g., a cron-like scheduler firing millions of identical tasks). For this system, where jobs have user-assigned priorities and dependency chains, the heap is the correct default. A timing wheel could be added as an alternative scheduler for high-volume, low-priority-criteria job types.

## Worker Design

### Recursive setTimeout vs setInterval

`setInterval` schedules the next execution at a fixed interval regardless of how long the current tick takes. If a tick runs long (e.g., a handler blocks on an external API for 30s), the next tick starts immediately after. You get back-to-back executions with no gap. If the tick throws an unhandled error, `setInterval` keeps firing into a broken state.

Recursive `setTimeout` eliminates both problems. The next tick is scheduled in the `finally` block of the current tick. If the current tick takes 5s, the next tick fires 1s after that. The interval is a *minimum* gap, not a fixed cadence. If an unhandled error propagates out of `tick()`, the `finally` block still runs and schedules the next tick. The worker is self-healing.

```typescript
private scheduleNext(): void {
  this.timer = setTimeout(() => {
    void this.tick().finally(() => {
      this.scheduleNext();
    });
  }, WORKER_INTERVAL_MS);
}
```

### The pessimistic lock (duplicate protection)

Before executing a handler, the worker claims the job with:

```sql
UPDATE jobs
SET status = 'processing', "startedAt" = NOW()
WHERE id = :id AND status = 'pending'
```

This is a row-level write lock. If two workers (or two ticks of the same worker) try to claim the same job, exactly one will see `affected > 0`. The loser sees 0 rows updated and silently returns. The `UPDATE` happens inside a transaction, so Postgres serializes concurrent writes to the same row. No application-level locking, no distributed mutex, no race condition.

The check-and-set is atomic because the `WHERE status = 'pending'` condition makes the UPDATE conditional. If another worker already flipped the status to `processing`, this worker's UPDATE affects 0 rows.

### Dependency check before execution

After claiming the job, the worker queries all `dependencyIds` and checks that every one has `status = completed`. If not, the job is re-queued:

- `status` set to `pending`
- `scheduledAt` set to `now + 10s`
- `startedAt` set to `null` (cleared so it does not look stuck)

This is not a failure. It is a re-queue. The job goes back into the pool and will be picked up again after the delay. The 10s delay prevents tight spin loops where a job's dependencies will not be met for another hour but the worker re-checks every second.

### Cancellation

Cancellation only works on `pending` jobs. A client calls `PATCH /jobs/:id/cancel`. The service checks the current status first:

```ts
const job = await this.findOne(id);

if (job.status !== JobStatus.PENDING) {
  throw new BadRequestException(
    `Cannot cancel job with status ${job.status}. Only pending jobs can be cancelled.`,
  );
}

await this.jobsRepository.update(id, { status: JobStatus.CANCELLED });
this.sseService.emit('job_updated', { jobId: id, status: JobStatus.CANCELLED });
```

If the job is `processing`, the endpoint rejects with a 400. The in-flight worker execution completes normally and the result is preserved. This avoids the race where a cancellation request arrives during execution and the worker's result would overwrite the intended cancelled status.

## Retry and Backoff

### The three-attempt flow

1. Handler throws. `handleFailure` increments `retryCount` from 0 to 1.
2. Since 1 < 3 (maxRetries), the job is re-queued with `scheduledAt = now + delay`.
3. On the next pop, it fails again. `retryCount` becomes 2.
4. 2 < 3. Re-queued with a larger delay.
5. Third failure. `retryCount` becomes 3.
6. 3 >= 3. Job is marked `failed`, `inDlq = true`, error message saved.

### Backoff values

| Attempt | Base delay | With jitter (0.5 to 1.5x) |
|---|---|---|
| 1 | 1,000ms | ~500 to 1,500ms |
| 2 | 5,000ms | ~2,500 to 7,500ms |
| 3+ | 25,000ms | ~12,500 to 37,500ms |

**Jitter** applies a random +/-50% factor to each delay. Without jitter, if 100 jobs fail simultaneously, they all retry at exactly the same moment. That is a thundering herd. With jitter, retries spread across a window. The formula:

```typescript
const jitter = 1 - JITTER_FACTOR + Math.random() * JITTER_FACTOR * 2;
// With JITTER_FACTOR = 0.5: results in 0.5 to 1.5 range
return Math.floor(baseDelay * jitter);
```

### `scheduledAt` as the retry mechanism

Retries set `scheduledAt` to `now + delayMs`. There is no separate retry queue, no retry topic, no retry counter table. The scheduler's feed query (`WHERE scheduledAt <= now() AND status = 'pending'`) naturally picks up retried jobs when their time comes. This is a key design principle: **the same mechanism handles first-run jobs and retries**.

### After the third failure

The job is set to:
- `status: 'failed'`
- `inDlq: true`
- `errorMessage: '<last error>'`

The scheduler's feed query filters on `status = 'pending'`, so DLQ jobs are invisible to the scheduler. They sit in the database until an engineer inspects them via the DLQ endpoint or manually retries them.

## Dead-Letter Queue

### In-database boolean flag

The DLQ is not a separate table or queue. It is a boolean flag: `inDlq: true` on the `jobs` table. When `retryCount >= maxRetries`, the worker sets this flag in the same UPDATE that marks the job as failed. No row movement, no copying to a DLQ table, no separate lifecycle.

### What an engineer does with it

1. Hits `GET /jobs/dlq`. Returns all jobs where `inDlq = true`, including their `errorMessage`.
2. Reads the error, investigates (flaky dependency? bad payload? transient outage?).
3. If the root cause is fixed, hits `POST /jobs/:id/retry`. Resets `retryCount` to 0, clears `errorMessage`, flips `inDlq` to `false`, sets `status` to `pending`, `scheduledAt` to now.
4. The job goes back through the normal scheduling pipeline.

### The threshold

When a job lands in the DLQ and the total DLQ count reaches **10 or more**, the worker creates a `dlq_alert` job at priority 0 (highest). A registered `DlqAlertHandler` receives it. Currently the handler logs a warning. It is a swap point for a real email or notification handler.

The threshold check uses `>= 10` with a one-hour cooldown. If the count is already at 15 and a new job enters the DLQ, no alert fires because the cooldown has not elapsed. After one hour, the next DLQ entry triggers a fresh alert. This prevents alert fatigue while ensuring sustained DLQ pressure is not silently ignored.

The threshold of 10 was chosen because:
- Sporadic single failures (network blips, transient DB contention) happen in normal operation. A threshold of 1 would fire alerts for background noise.
- 10 indicates a systemic problem. If 10 different jobs have exhausted their retries, something is likely broken.
- It is low enough to catch problems early in a 50k-job system.

### What happens on re-failure

A manually retried DLQ job goes through the full retry cycle again. If it exhausts `maxRetries`, it lands back in the DLQ with an updated `errorMessage`. The count check fires again if the total is `>= 10` and the cooldown has elapsed.

## DAG Engine (Dependency Resolution)

### Cycle detection at creation time

When a job is created with dependencies, the service runs a DFS (depth-first search) cycle detection:

```
for each dependencyId:
  visit(jobId):
    if jobId == targetId or jobId is in "visiting" set -> CYCLE FOUND
    if jobId is in "visited" set -> skip (already checked)
    add jobId to "visiting" set
    for each dep of jobId:
      visit(dep)
    remove from "visiting", add to "visited"
```

A cycle produces a `400 Bad Request` with `"Cycle detected in job dependencies (DAG validation failed)"`. The job is not saved.

This runs on both `POST /jobs` (create) and `PATCH /jobs/:id` (update). Self-dependencies are caught before the DFS even runs.

### Dependency enforcement at execution time

After the worker claims a job, before executing the handler:

```typescript
const deps = await this.jobsRepository.findBy({ id: In(job.dependencyIds) });
const allCompleted = deps.every(d => d.status === 'completed');
```

If any dependency is not `completed`, the job is re-queued with a 10s delay. This is **not a failure**. It is a deferral. The job's `retryCount` is not incremented. The log event is `dependency_not_met`, not `retry_scheduled` or `failed`.

Why re-queue and not fail? Because dependencies are expected to resolve eventually. A failure would consume a retry attempt, and the retry backoff would delay the job longer than necessary. The 10s re-queue is a short, fixed delay that gives the upstream job time to complete.

### Example: three-job chain

1. `POST /jobs` with `{ type: 'generate_report', dependencyIds: [] }`. Saved as `job-A`.
2. `POST /jobs` with `{ type: 'upload_file', dependencyIds: ['job-A'] }`. Saved as `job-B`.
3. `POST /jobs` with `{ type: 'send_email', dependencyIds: ['job-B'] }`. Saved as `job-C`.

**Execution:**
- Scheduler picks up `job-A` (no dependencies). Worker claims it, handler runs (`generate_report`), completes.
- Scheduler picks up `job-B`. Worker claims it, checks dependencies: `job-A` is `completed`. Executes handler (`upload_file`), completes.
- Scheduler picks up `job-C`. Worker claims it, checks dependencies: `job-B` is `completed`. Executes handler (`send_email`), completes.

If `job-B` had been dequeued before `job-A` completed (possible if the scheduler feeds both before the worker processes them), the dependency check would fail, and `job-B` is re-queued with a 10s delay. By that time, `job-A` would likely be complete, and the next attempt would pass.

## Starvation Prevention

### Priority inversion in a strict heap

In a strict priority-ordered heap, high-priority jobs (priority 1) always come out before low-priority jobs (priority 5). If new priority-1 jobs keep arriving, a priority-5 job that has been waiting for hours never gets dequeued. It starves.

### Periodic sweep with priority boost

Every 30 seconds, a sweep queries for pending jobs that:

- Are past their `scheduledAt` by more than 2 minutes (`scheduledAt < now - 2min`)
- Have priority > 1 (cannot boost below the floor)
- Have not been boosted in the last 30 seconds (`lastPriorityBoostedAt IS NULL OR lastPriorityBoostedAt < now - 30s`)

For each match, priority is decreased by 1: `GREATEST("priority" - 1, 1)`. The `lastPriorityBoostedAt` is set to now.

After the boost, the heap is cleared and re-fed from the database. The boosted jobs now have higher priority and bubble up to the correct position. The rebuild only happens when the sweep actually finds and boosts jobs. If no jobs match the eligibility criteria, the heap stays untouched and no query runs beyond the initial UPDATE.

### Why it is approximate

The boost is coarse: every eligible job gets exactly one level per sweep. A job at priority 10 that has been starving for an hour might need 9 sweeps (4.5 minutes) to reach priority 1. A job at priority 2 reaches priority 1 in one sweep. The goal is not fairness. It is preventing indefinite starvation. A job that has been waiting for 2+ minutes will eventually become the highest-priority job in the heap.

The 2-minute threshold is derived from the expected worst-case processing time for a typical job (most jobs complete within seconds). If a job has been pending for 2 minutes past its scheduledAt while newer jobs that were scheduled later are being dequeued, something is wrong. It is starving.

## Recurring Jobs

### How intervals work

When a job is created with a non-null `interval` field, it is a recurring job. The interval values are:

| Value | Meaning | Approximate ms |
|---|---|---|
| `every_1_minute` | Every minute | 60,000 |
| `every_5_minutes` | Every 5 minutes | 300,000 |
| `every_15_minutes` | Every 15 minutes | 900,000 |
| `every_30_minutes` | Every 30 minutes | 1,800,000 |
| `hourly` | Every hour | 3,600,000 |
| `daily` | Every day | 86,400,000 |
| `weekly` | Every week | 604,800,000 |
| `monthly` | Every ~30 days | 2,592,000,000 |

Monthly is approximate: exactly 30 days. Not calendar-accurate.

### New row per execution

When a recurring job's handler succeeds, the worker:

1. Marks the current job as `completed`, preserving its execution record.
2. **Inserts a new job row** with `scheduledAt = now + interval`, same `type`, `payload`, `priority`, `maxRetries`, `dependencyIds`.
3. Emits a `job_created` SSE event.

### Why insert a new row instead of resetting `scheduledAt`?

Audit trail. If we reset `scheduledAt` on the existing row, we lose the completed-at timestamp, the execution history, and the ability to track how long each cycle took. With a new row per execution, the `completedAt` on the old row is preserved, the `job_logs` table has a complete execution record, and a simple query can calculate cycle duration: `SELECT completedAt - createdAt FROM jobs WHERE type = 'send_email'`.

## SSE (Server-Sent Events)

### Why SSE over WebSockets

One-directional data flow. The server needs to push job state changes to the frontend. The frontend never sends commands over this channel (it uses REST for that). SSE is:
- Simpler. No handshake protocol, no reconnection logic, no message framing.
- Native browser support via `EventSource`.
- HTTP-based. Works through standard proxies and load balancers.
- Auto-reconnecting. The browser `EventSource` API automatically reconnects on drop.

### RxJS Subject and @Sse() decorator

A global `SseService` holds an RxJS `Subject<MessageEvent>`. The `GET /jobs/stream` endpoint wraps the subject as an observable and returns it via NestJS's `@Sse()` decorator, keeping the connection open:

```typescript
@Sse('stream')
jobEvents(): Observable<MessageEvent> {
  return this.sseService.events$;
}
```

### Disconnect handling

RxJS's `Observable` contract handles cleanup. When the client disconnects, NestJS unsubscribes from the observable, which triggers `Subject` cleanup. Without this, the `Subject` would accumulate references to disconnected clients' response objects, leaking memory. Each disconnected-but-uncollected client keeps the Node.js response stream open and prevents garbage collection.

### Event types

| Event | Payload | When it fires |
|---|---|---|
| `job_created` | `{ jobId, status, type, priority }` | After `POST /jobs` saves the new row, and when a recurring job spawns its next execution |
| `job_updated` | `{ jobId, status }` + optionally `retryCount`, `inDlq` | Worker claims job -> `processing`; success -> `completed`; failure -> `failed` + `inDlq: true`; retry -> `pending` + `retryCount`; cancel -> `cancelled`; manual DLQ retry -> `pending` |
| `dlq_alert` | `{ dlqCount, alertJobId }` | When a job enters the DLQ and the total DLQ count reaches exactly 10 |

## Logging

### NestJS Logger and job_logs table

1. **NestJS Logger**: structured JSON output to stdout. Used for operational monitoring and debugging. The `Logger` instance includes the class name for context.
2. **`job_logs` table**: an append-only audit trail per job. Every state transition writes an event with a human-readable message. Events include: `processing`, `completed`, `failed`, `retry_scheduled`, `dependency_not_met`, `dlq_alert_triggered`, and the log events from each handler's lifecycle.

### Why two log destinations

The Logger is ephemeral: rotated daily, lost on container restart, not queryable by job ID. The `job_logs` table survives restarts and supports queries like "how many times did this job retry?" and "what was the error on the third attempt?" without digging through log files.

### Every event and its context

| Event | Context carried in `message` |
|---|---|
| `processing` | `"Worker picked up job"` |
| `completed` | `"Job completed successfully"` |
| `failed` | `"Failed after N retries: <error message>"` |
| `retry_scheduled` | `"Retry N/3 in Xms: <error message>"` |
| `dependency_not_met` | `"Re-queued with 10000ms delay"` |
| `dlq_alert_triggered` | `"DLQ count hit 10"` |

## Duplicate Protection

Every job claim uses:

```typescript
const result = await this.jobsRepository
  .createQueryBuilder()
  .update(Job)
  .set({ status: JobStatus.PROCESSING, startedAt: new Date() })
  .where('id = :id', { id: job.id })
  .andWhere('status = :status', { status: JobStatus.PENDING })
  .execute();

return (result.affected ?? 0) > 0;
```

This is a **conditional update**. The `WHERE status = 'pending'` clause makes the update a no-op if another worker already claimed the job. The `UPDATE` acquires a row-level write lock, so two concurrent updates to the same row are serialized by Postgres. Exactly one worker sees `affected > 0`.

Application-level locking (e.g., a Redis mutex, an in-memory lock map) is not sufficient because:
- Two worker instances in separate processes cannot share an in-memory lock.
- A distributed lock (Redis) adds infrastructure and latency.
- The DB already has the lock mechanism built in. A conditional UPDATE with a row lock is the simplest thing that works across any number of worker instances.

The heap pop and the DB claim are not atomic. Two ticks of the same worker could pop the same entry if the heap is not properly guarded. The `inHeap` set prevents this within a single process: once popped, the ID is removed from the set before the next pop. The DB-level claim is the cross-instance safety net.

## Health Endpoint

`GET /health` returns a JSON object with `status`, `db`, and `timestamp`. It checks database connectivity by running `SELECT 1`. If the query fails, `status` is `degraded` and `db` is `error`. If it succeeds, both are `ok`.

For deployment health checks, Nginx upstream verification, and container orchestration liveness probes. No authentication required. Returns immediately without blocking on other services.
